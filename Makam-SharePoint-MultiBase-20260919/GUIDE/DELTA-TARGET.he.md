# קבלת היעד שנותרה לצוות DevOps

מצב נוכחי לכל הסעיפים: **BLOCKED — TARGET ENVIRONMENT REQUIRED**. אין גישה לחווה או לשרת הארגון. יש לשמור תאריך, מבצע, גרסאות, origin/endpoint, תוצאה וראיה מסוננת מכל סעיף; אין לשמור כותרת Authorization, אסימונים, cookies או סודות.

1. ב־staging עם ה־Node/IISNode המאושרים: cold start ו־recycle דרך Named Pipe; health מול Mongo הארגוני, Sharp מקומי, קריאה/כתיבה והורדת PNG/Excel. ודאו שהנתיב ל־Node מוחלט, HTTPS נאכף, ואין חשיפת קוד/הגדרות/יומנים.
2. Windows Authentication פעיל ב־session הפיזי; AUTH_USER/AUTH_TYPE מתקבלים מקידום native. בקשה אנונימית אינה מקבלת session. כותרות זהות שסיפק לקוח (כולל כפולות, מקפים/קו תחתון ו־x-iisnode-*) נחסמות **לפני** קידום IIS. אין לבדוק זאת באמצעות הזרקת כותרות ישירות ל־Node ולהסיק שזה IIS.
3. OPTIONS מ־SharePoint מורשה מצליח ללא challenge; origin זר וכותרות זהות ב־preflight נדחים. הממשק מהספרייה המקוננת בפועל נטען, מקבל session מ־IIS ומציג את sAMAccountName הנכון, כולל שני חשבונות Windows שונים. אם זהות SharePoint שונה מזהות Windows המוצגת ל־API, עצרו ופתרו את תצורת ה־SSO; אין להסתמך על JavaScript להעברת זהות.
4. משתמש לא משויך/לא פעיל נדחה. ביטול משתמש/הרשאה/session משפיע על הבקשה הבאה; שינוי baseId אינו מאפשר מידע מבסיס אחר. בדקו את הרמות הארגוניות ואת מסך הפיקוד בפועל.
5. שני משתמשים דרך IIS אינם חולקים מכסה: 40 החלפות session למשתמש בדקה, ה־41 נדחה ב־429, ומשתמש אחר ממשיך. שינוי XFF אינו מאפס מכסה. התצורה הנמסרת היא process אחד **לכל endpoint פיזי**; חלון המכסה בזיכרון נפרד לכל תהליך ומתאפס ב־recycle. אם קיימים כמה workers/שרתים או ממפים גם endpoint נוסף באופן עצמאי, נדרש store משותף/מדיניות IIS לפני הרחבת ההתקנה.
6. אם דואר מופעל: בדיקת SMTP פנימי, נמענים נכונים בכל בסיס ומצבי partial/unknown; אין שליחה עיוורת חוזרת אחרי recycle. תוצאות transport הבדיקה המקומי אינן הוכחת SMTP.

את הדגל TRUSTED_IDENTITY_VERIFIED מסמנים רק אחרי הוכחת גבול האימות ב־staging ואישור DevOps. שמרו את TARGET-CHECKLIST המלא לרגרסיית פריסה; הרשימה הזו מצמצמת את השערים שאי אפשר להוכיח במחשב המקומי.
